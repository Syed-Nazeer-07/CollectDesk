# CollectDesk — Render + MongoDB Atlas demo deployment

**Scope:** fictional data, private GitHub source, shareable demo URL. This is **not** a production debt-collection platform. Do not upload real invoices, customer information, or bank records.

**Existing deployment (8 November 2026):** The service is already provisioned as [collectdesk-preview-ah80](https://dashboard.render.com/web/srv-dbnvfl3rjlhs73a0h5jg), with the public demo at https://collectdesk-preview-ah80.onrender.com/login and a dedicated MongoDB Atlas demo cluster. Sections 1–2 below are for **reprovisioning**, not required again on the existing service. Keep credentials private and do not create a duplicate service.

## Architecture

- One Render **web service** built from `Dockerfile.render` runs Next.js on Render's public `PORT` (normally 10000) and Express privately inside the same container on port 4000.
- Browser requests use a same-origin Next.js proxy. Express accepts state-changing requests only from the exact `WEB_ORIGIN` or Render-provided `RENDER_EXTERNAL_URL`.
- MongoDB Atlas stores fictional cases persistently. No MongoDB process or database files are hosted on Render's ephemeral disk.
- `/api/health` returns **200** only when both Next.js and the internal MongoDB-backed API are available.

## 1. Prepare a dedicated Atlas **free** cluster

1. Open https://cloud.mongodb.com/ and create a new Atlas project specifically for CollectDesk demo data.
2. Create a Free (M0) cluster if your account is eligible. Use a nearby region when available.
3. Add a **database user** with a randomly generated unique password and limited `readWrite` privileges for the **collectdesk_demo** database. Avoid a project-wide admin account.
4. In **Network Access**, restrict Atlas to the service's actual **Render outbound CIDR ranges**, which are listed under the service's **Connect → Outbound** tab. Render documents a region-specific set of shared outbound IP ranges (not a single exclusive static IP). If a throwaway demo temporarily uses `0.0.0.0/0`, it is more exposed; tighten it to the listed CIDRs after confirming connections. See https://render.com/docs/outbound-ip-addresses. Do not copy IPs from another service or remove working access before adding the confirmed ranges.
5. Under **Connect → Drivers**, copy the SRV connection URI. Specify `/collectdesk_demo` as the database **in the URI path**, before the `?` query string:

   `mongodb+srv://DB_USER:URL_ENCODED_DB_PASSWORD@YOUR_CLUSTER.mongodb.net/collectdesk_demo?retryWrites=true&w=majority`

   Replace the placeholder values **only in Render's secret environment variable editor**. URI-encode reserved characters in database usernames and passwords.

**Important:** The demo seed refuses any database whose URI path is not `collectdesk_demo` or `collectdesk_ci_demo`. Never point the demo seed to an existing real database.

## 2. Create the Render service

1. Sign in at https://dashboard.render.com/ and connect your GitHub account if needed, granting access to your **private** `Syed-Nazeer-07/CollectDesk` repository.
2. Select **New → Blueprint** and choose that repository. Render detects the root `render.yaml`.
3. Review the settings: one **Free** web service named `collectdesk-preview`, `Dockerfile.render`, Singapore region, and deploys gated on CI checks passing. Do not enable paid compute unless you choose to.
4. Render prompts for the following **secret** environment variables during Blueprint creation:
   - `MONGODB_URI`: your Atlas connection URI above.
   - `DEMO_SEED_PASSWORD`: a **new, unique** password of at least 12 characters. Do not reuse passwords shared in chat or your local Compose password.
5. `JWT_SECRET` is generated by Render automatically. `NODE_ENV` is `production`. Seed fictional accounts **once** for the initial deployment using `SEED_DEMO_ON_START=true`, then set it to **false** to avoid slow or disruptive re-seeding after free-instance restarts. The existing deployment already has it set to `false`.
6. Start the initial deployment. Render provides its actual HTTPS `onrender.com` URL. Do **not** assume the final hostname before Render assigns it.

Render injects `RENDER_EXTERNAL_URL`, which the API uses for exact origin validation. If you later add a custom domain, set `WEB_ORIGIN` in the Render environment to the exact `https://` domain used by the browser.

## 3. Verify the deployed demo

- `https://YOUR_ASSIGNED_RENDER_URL/api/health` should return `{"ok":true}` and HTTP **200**.
- `https://YOUR_ASSIGNED_RENDER_URL/login` should load the login interface.
- Use `admin@demo.collectdesk.test` and the new **hosted** `DEMO_SEED_PASSWORD`.
- Verify login, dashboard, cases, new creditor invoice, admin review, operator assignment, receipt verification, and logout. Use fictional data only.
- Check Render's service logs for MongoDB errors and listen/port errors.
- Do not post your demo password or Atlas connection string in GitHub issues, screenshots, chat, or README.

An idle Free web service sleeps and may be slow on its first request; a live external test observed **two 95-second request timeouts** before the third health check succeeded. Test opening the preview before important demos, but do not use artificial pings that drain the workspace's shared free hours. Reliable no-wait operation requires a suitable always-on plan.

## Security, costs, and limitations

- The web service is internet-reachable; the login screen is **not** an invite-only/private service. Share the password only with the intended reviewer, and rotate it if exposed. The code has not undergone an external penetration test.
- Render Free web service capacity and hours/bandwidth are limited; check your Render dashboard for quota and pricing. It is not reliable production hosting.
- Keep all banking/customer data **out** of the demo. The financial ledger and per-case lock need database transactions, reconciliation, audit logging, access reviews, and legal review before any real use.
- `SEED_DEMO_ON_START` should remain `false` on an already seeded demo. Resetting only the Render demo password does not update existing user password hashes: deliberate reseeding is required for credential rotation, followed by setting the flag back to `false`.
- `.env.compose`, `.env`, and private secrets must remain untracked and excluded from Docker build context.

## Rollback and debugging

- GitHub Actions `CollectDesk checks` tests TypeScript, domain/API rules, browser workflows, the Render image, and a hosted container smoke test.
- In Render, inspect **Deploys → Logs** and choose **Manual Deploy** or **Rollback** to a prior healthy deployment. Never copy Atlas credentials into support logs.
- If `/api/health` is 503: check Atlas network access, database user, connection string, and seeded DB name.
- If login returns 401: ensure the password matches `DEMO_SEED_PASSWORD`. For a throwaway demo you may deliberately rerun seed, but do not run it against real datasets.
- If state-changing requests return 403: check `WEB_ORIGIN` against the precise public HTTPS origin, including protocol and hostname.
